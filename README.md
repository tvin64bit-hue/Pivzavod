# Сайт «Лаборатория живого пива» (пивзавод74)

Статический сайт крафтовой пивоварни из Челябинска, собранный по
[ТЗ](./TZ-pivzavod74-final.md). Astro 5, ноль JS по умолчанию, точечные
скрипты только там, где ТЗ требует интерактива.

## Быстрый старт

```bash
npm install
npm run dev      # http://localhost:4321
npm run build    # сборка в dist/
npm run preview  # предпросмотр собранного
```

**Никаких `.env` для этого не нужно.** Токен Telegram и chat_id читает только
обработчик формы `functions/api/lead.ts` — он выполняется на стороне Cloudflare
и в сборку Astro не входит. Без переменных сборка проходит полностью:
все 26 страниц, без ошибок и предупреждений.

Единственное, что не заработает в `npm run dev`, — **отправка формы заявки**.
Каталог `functions/` понимает только Cloudflare, а dev-сервер Astro его не
обслуживает, поэтому `POST /api/lead` вернёт 404, и форма покажет
«Не удалось отправить заявку — позвоните нам». Это ожидаемо, а не поломка:
так и задумано, чтобы форма не притворялась отправленной.

Если нужно проверить и форму тоже — поднимите тот же рантайм, что в продакшене:

```bash
cp .env.example .dev.vars   # впишите токен бота и chat_id
npm run build
npm run preview:cf          # wrangler pages dev dist
```

Тогда заработают и `/api/lead`, и редиректы из `_redirects`, и заголовки
из `_headers`. Файл `.dev.vars` в git не попадает.

забыть о них нельзя.

| **Актуальность оптовых цен** | `/gde-kupit/opt` | Цены с донора выводятся как есть, с пометкой |
| **Карта с 6 метками точек продаж** | `/gde-kupit/tochki-prodazh` | Показана карта с одной меткой — офис на Карпинского |

### Как подставить карту с несколькими метками

1. Откройте [конструктор Яндекс.Карт](https://yandex.ru/map-constructor/),
   поставьте метки на все шесть точек продаж.
2. Нажмите «Сохранить и продолжить» → «Получить код карты» → вкладка
   «Ссылка на карту», скопируйте адрес вида
   `https://yandex.ru/map-widget/v1/?um=constructor%3A…&source=constructor`.
3. Вставьте его в `src/data/site.ts`:

```ts
export const maps = {
  outletsConstructorUrl: 'https://yandex.ru/map-widget/v1/?um=constructor%3A…',
  …
};
```

Разметку менять не нужно — компонент сам предпочтёт эту ссылку поиску по адресу,
а предупреждающая плашка исчезнет.

## Миграция контента с сайта-донора

**Скрипт написан и протестирован, но не запущен: домен `pivzavod74.ru`
закрыт сетевой политикой того окружения, где собирался сайт** — egress-прокси
отвечает `403` на `CONNECT` и для `curl`, и для встроенного веб-фетчера.
Разрешение `WebFetch(domain:pivzavod74.ru)` в `.claude/settings.json` открывает
инструмент, но не сетевую политику окружения.

Запустите миграцию с машины, у которой есть доступ к донору:

```bash
npm run migrate -- --limit 3 --dry-run   # проверить парсинг на трёх страницах
npm run migrate -- --limit 3             # записать три страницы и убедиться в результате
npm run migrate                          # полный проход по 153 URL
npm run migrate -- --resume              # продолжить, пропуская уже скачанное
```

Что делает скрипт (по разделу 8 ТЗ):

- читает адреса из `sitemap_urls.txt` и берёт из них 144 статьи;
  девять оставшихся — корень и витрины разделов («Новости/», «Дегустация/»),
  это не материалы, а списки анонсов, и переносить их незачем;
- обходит их **последовательно с задержкой 5 секунд** — это `Crawl-delay: 5`
  из `robots.txt` донора, никакого параллельного обхода;
- складывает сырой HTML в `assets/legacy-content/raw/` (в git не попадает);
- вытаскивает заголовок, дату публикации, текст и адреса `<img>`;
- качает изображения в `public/images/legacy/` — только по адресам из
  `<img>` на страницах, потому что листинг `/images/` на доноре отдаёт 403;
- пишет записи в `src/content/blog/*.md` с **оригинальными датами публикации**;
- берёт изображения только из тела статьи, а не со всей страницы: иначе
  обложкой записи стал бы логотип шаблона, а в галерею попала бы обвязка;
- запоминает уже опрошенные адреса картинок — логотип и кнопки шаблона
  повторяются на всех страницах, а битый хотлинк иначе ловил бы
  30-секундный таймаут по 144 раза;
- битые хотлинки на мёртвые домены (старый `vkontakte.ru` и подобные)
  логирует в `assets/legacy-content/migration-report.json` и пропускает,
  не обрывая миграцию.

Полный проход — **не меньше 12 минут** только на задержках между статьями,
плюс по 5 секунд на каждое новое изображение; реально ждать около часа.
Повторные и уже скачанные картинки сети не касаются.

### Запуск через GitHub Actions

Если донор недоступен с вашей машины, обход можно выполнить на раннере
GitHub: вкладка **Actions** → «Миграция контента с донора» → **Run workflow**.
В поле «Use workflow from» выберите рабочую ветку — туда же workflow
закоммитит результат. Параметры те же: `limit`, `dry_run`, `resume`.

После миграции:

1. Просмотрите записи с `draft: true` — так помечены те, где не удалось
   распознать дату публикации.
2. Проверьте раскладку по категориям во фронтматтере: скрипт назначает её
   по разделу пути на доноре, а ТЗ требует ровно шесть категорий.
3. Изображения подставятся в страницы сами — компонент `LegacyImage`
   проверяет наличие файла на сборке. До миграции на их месте видна рамка
   с именем ожидаемого файла.

### Тексты архивных статей

Раздел 8 ТЗ: тексты переносятся **как есть**, с оригинальными датами.
Архивные факты внутри старых статей не редактируются — это исторические
записи. Колонки категории «Позиция отрасли» переносятся как официальная
позиция компании и Союза пивоваров.

## Деплой: Cloudflare Pages

Репозиторий готов к развёртыванию: настройки сборки лежат в `wrangler.toml`,
версия Node — в `.nvmrc`, обработчик формы — в `functions/`. Всё проверено
локально на настоящем рантайме Workers через `wrangler pages dev`.

### Подключение через панель

1. [dash.cloudflare.com](https://dash.cloudflare.com) → **Workers & Pages** →
   **Create** → вкладка **Pages** → **Connect to Git**.
2. Авторизуйте GitHub, выберите репозиторий `tvin64bit-hue/Pivzavod`.
3. Ветка для продакшена — та, которую разворачиваете (`main` после мержа PR).
4. Настройки сборки:
   - Framework preset: **Astro**
   - Build command: `npm run build`
   - Build output directory: `dist`
5. **Save and Deploy**. Первая сборка занимает 2–3 минуты.

### Переменные окружения

Settings → **Variables and Secrets**. Без них форма заявки честно отвечает
об ошибке и просит позвонить — она не делает вид, что заявка ушла.

| Имя | Тип | Значение |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | **Secret** | токен от @BotFather |
| `TELEGRAM_CHAT_ID` | Variable | id чата для уведомлений |
| `ALLOWED_ORIGIN` | Variable, необязательно | `https://<ваш-домен>` — отсекает запросы с чужих сайтов |
| `SITE_URL` | Variable, необязательно | канонический домен, если он не `pivzavod74.ru` |

Токен задавайте именно как **Secret**: обычные переменные видны в панели
в открытом виде и попадают в логи сборки.

После добавления переменных нужен повторный деплой — Deployments →
**Retry deployment**, иначе функция их не увидит.

### Свой домен

Custom domains → Set up a domain → `pivzavod74.ru`. Если домен уже в
Cloudflare, DNS пропишется сам; иначе смените NS у регистратора на выданные
Cloudflare. После привязки задайте `SITE_URL`, чтобы канонические ссылки
и `sitemap.xml` указывали на рабочий домен.

### Локальная проверка перед деплоем

```bash
cp .env.example .dev.vars   # заполните токен и chat_id
npm run build
npm run preview:cf          # wrangler pages dev dist
```

Поднимется тот же рантайм Workers, что и в продакшене: заработают функция
`/api/lead`, редиректы из `_redirects` и заголовки из `_headers`.
Файл `.dev.vars` в git не попадает.

Развернуть из командной строки, минуя панель: `npm run deploy`
(потребует `npx wrangler login`).

### Что проверено на wrangler pages dev

- Все 14 редиректов со старых адресов Joomla ведут в нужные разделы.
- Кириллица в `_redirects` записана процентным кодированием: Cloudflare
  кодирует пути правил при разборе файла, и строка с сырой кириллицей
  не совпала бы ни с чем.
- Заголовки безопасности и годовой кэш хэшированных ассетов отдаются.
- Форма отбивает пустые заявки и кривые телефоны кодом 400, ловит ботов
  в honeypot, а при недоступном Telegram возвращает 502.
- На методы, кроме POST, маршрут `/api/lead` отвечает 404.

### Как получить chat_id

1. Создайте бота через [@BotFather](https://t.me/BotFather), скопируйте токен.
2. Добавьте бота в группу, куда должны падать заявки, и напишите туда любое сообщение.
3. Откройте `https://api.telegram.org/bot<ТОКЕН>/getUpdates` — нужное значение
   лежит в `message.chat.id` (у групп оно отрицательное).

## Структура

```
src/
  components/      Сквозные и страничные компоненты
  content/blog/    Записи блога (сюда пишет скрипт миграции)
  data/            Весь копирайт и справочные данные из ТЗ
  layouts/         BaseLayout: head, SEO, Schema.org
  pages/           Маршруты, повторяют карту сайта из раздела 2 ТЗ
  styles/          tokens.css — дизайн-система, global.css — база
functions/api/     Cloudflare Pages Function: форма → Telegram
scripts/           migrate-donor.mjs — миграция с донора
public/            robots.txt, _redirects, _headers, favicon, OG
assets/            Сырые материалы с донора (в git не попадают)
```

Весь текст с сайта вынесен в `src/data/site.ts` и `src/data/content.ts` —
страницы его не хардкодят, правки контента не требуют лезть в разметку.

## Совместимость со старыми адресами

`public/_redirects` переводит разделы Joomla-донора (`/index.php/…`) на новую
структуру 301-редиректами, чтобы ни один старый URL не отдавал 404.
Точечные редиректы отдельных записей блога имеет смысл дописать после
миграции — у каждой записи в фронтматтере сохраняется `legacyUrl`.
