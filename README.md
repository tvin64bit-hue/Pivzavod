# Сайт «Лаборатория живого пива» (пивзавод74)

Статический сайт крафтовой пивоварни из Челябинска, собранный по
[ТЗ](./TZ-pivzavod74-final.md). Astro 5, ноль JS по умолчанию, точечные
скрипты только там, где ТЗ требует интерактива.

## Быстрый старт

```bash
npm install
npm run dev      # http://localhost:4321
npm run build    # сборка в dist/
npm run preview  # предпросмотр собранного
```

**Никаких `.env` для этого не нужно.** Настройки почты читает только сервис
приёма заявок `server/lead.mjs`, а он в сборку Astro не входит. Без переменных
сборка проходит полностью, без ошибок и предупреждений.

Единственное, что не заработает в `npm run dev`, — **отправка формы заявки**:
dev-сервер Astro отдаёт только страницы, поэтому `POST /api/lead` вернёт 404,
и форма покажет «Не удалось отправить заявку — позвоните нам». Это ожидаемо,
а не поломка: так и задумано, чтобы форма не притворялась отправленной.

Если нужно проверить и форму — поднимите сервис заявок рядом:

```bash
cp deploy/pivzavod74.env.example .env   # впишите MAIL_TO и SMTP_*
set -a && . ./.env && set +a
npm run serve                            # слушает 127.0.0.1:8787
```

Файл `.env` в git не попадает. Astro dev-сервер `/api/` не проксирует, поэтому
для сквозной проверки формы удобнее собрать сайт и открыть его через nginx —
как на сервере.

### Windows и PowerShell

Нужен Node 20 или новее — поставьте LTS с [nodejs.org](https://nodejs.org/),
затем закройте и откройте PowerShell заново, чтобы обновился PATH.

```powershell
node -v      # должно быть v20 или выше
git clone https://github.com/tvin64bit-hue/Pivzavod.git
cd Pivzavod
git checkout claude/website-creation-spec-b30y7d
npm install
npm run dev
```

Если `npm` падает с сообщением, что «выполнение сценариев отключено в этой
системе», это политика PowerShell блокирует `npm.ps1`. Лечится один раз:

```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

Либо, не меняя политику, вызывайте `npm.cmd` вместо `npm`:

```powershell
npm.cmd install
npm.cmd run dev
```

Останавливается сервер по Ctrl+C. Порт по умолчанию 4321; занят —
запустите `npm run dev -- --port 4322`.

Остальное закрыто: состав руководства, вакансии и оптовые цены заказчик

SPA снят.

### Как заменить карту

Карта с шестью точками уже подключена. Если понадобится пересобрать:

1. Откройте [конструктор Яндекс.Карт](https://yandex.ru/map-constructor/),
   расставьте метки.
2. «Сохранить и продолжить» → «Получить код карты». Годится любая из двух
   ссылок, которые он предлагает, — и «ссылка на карту» (`/maps/?um=…`),
   и код для вставки (`/map-widget/v1/?um=…`): компонент приводит первую
   ко второй сам.
3. Вставьте её в `maps.outletsConstructorUrl` в `src/data/site.ts`.

Разметку менять не нужно.

## Миграция контента с сайта-донора

**Скрипт написан и протестирован, но не запущен: домен `pivzavod74.ru`
закрыт сетевой политикой того окружения, где собирался сайт** — egress-прокси
отвечает `403` на `CONNECT` и для `curl`, и для встроенного веб-фетчера.
Разрешение `WebFetch(domain:pivzavod74.ru)` в `.claude/settings.json` открывает
инструмент, но не сетевую политику окружения.

Запустите миграцию с машины, у которой есть доступ к донору:

```bash
npm run migrate -- --limit 3 --dry-run   # проверить парсинг на трёх страницах
npm run migrate -- --limit 3             # записать три страницы и убедиться в результате
npm run migrate                          # полный проход по 153 URL
npm run migrate -- --resume              # продолжить, пропуская уже скачанное
```

Что делает скрипт (по разделу 8 ТЗ):

- читает адреса из `sitemap_urls.txt` и берёт из них 144 статьи;
  девять оставшихся — корень и витрины разделов («Новости/», «Дегустация/»),
  это не материалы, а списки анонсов, и переносить их незачем. В блог
  попадают 127 записей: часть адресов на доноре вела на одну и ту же статью
  из разных разделов, дубли схлопываются по адресу-первоисточнику;
- обходит их **последовательно с задержкой 5 секунд** — это `Crawl-delay: 5`
  из `robots.txt` донора, никакого параллельного обхода;
- складывает сырой HTML в `assets/legacy-content/raw/` (в git не попадает);
- вытаскивает заголовок, дату публикации, текст и адреса `<img>`;
- качает изображения в `public/images/legacy/` — только по адресам из
  `<img>` на страницах, потому что листинг `/images/` на доноре отдаёт 403;
- пишет записи в `src/content/blog/*.md` с **оригинальными датами публикации**;
- берёт изображения только из тела статьи, а не со всей страницы: иначе
  обложкой записи стал бы логотип шаблона, а в галерею попала бы обвязка;
- запоминает уже опрошенные адреса картинок — логотип и кнопки шаблона
  повторяются на всех страницах, а битый хотлинк иначе ловил бы
  30-секундный таймаут по 144 раза;
- битые хотлинки на мёртвые домены (старый `vkontakte.ru` и подобные)
  логирует в `assets/legacy-content/migration-report.json` и пропускает,
  не обрывая миграцию.

Полный проход — **не меньше 12 минут** только на задержках между статьями,
плюс по 5 секунд на каждое новое изображение; реально ждать около часа.
Повторные и уже скачанные картинки сети не касаются.

### Запуск через GitHub Actions

Если донор недоступен с вашей машины, обход можно выполнить на раннере
GitHub: вкладка **Actions** → «Миграция контента с донора» → **Run workflow**.
В поле «Use workflow from» выберите рабочую ветку — туда же workflow
закоммитит результат. Параметры те же: `limit`, `dry_run`, `resume`.

После миграции:

1. Просмотрите записи с `draft: true` — так помечены те, где не удалось
   распознать дату публикации.
2. Проверьте раскладку по категориям во фронтматтере: скрипт назначает её
   по разделу пути на доноре, а ТЗ требует ровно шесть категорий.
3. Изображения подставятся в страницы сами — компонент `LegacyImage`
   проверяет наличие файла на сборке. До миграции на их месте видна рамка
   с именем ожидаемого файла.

### Тексты архивных статей

Раздел 8 ТЗ: тексты переносятся **как есть**, с оригинальными датами.
Архивные факты внутри старых статей не редактируются — это исторические
записи. Колонки категории «Позиция отрасли» переносятся как официальная
позиция компании и Союза пивоваров.

## Деплой: свой сервер (FirstVDS)

Сайт статический — nginx отдаёт готовые файлы. Динамическая часть одна: приём
заявок с формы, её обслуживает `server/lead.mjs`, который шлёт письмо по SMTP.
Ни базы, ни админки.

Пошаговая установка сервера с нуля — в **[deploy/README.md](./deploy/README.md)**.
Дальнейшие выкладки — одной командой:

```bash
SSH_TARGET=root@адрес-сервера npm run deploy
```

Скрипт собирает сайт, генерирует конфиг nginx, заливает статику и сервис,
ставит зависимости, перезапускает сервис и перечитывает nginx.

### Админка

`https://pivzavod74.ru/admin` — вход по логину и паролю, без GitHub и прочих
внешних сервисов. Внутри: список новостей с поиском по заголовку, кнопки
«изменить» и «удалить», создание записи, редактор с панелью форматирования,
загрузкой фотографий перетаскиванием и живым предпросмотром.

Пароль хранится хешем (scrypt из стандартной библиотеки Node), сессия — в
подписанной куке `HttpOnly; Secure; SameSite=Strict`. Пять неверных попыток
подряд с одного адреса — минута паузы, плюс ограничение частоты на уровне
nginx. Раздел закрыт от индексации и в `robots.txt`, и заголовком
`X-Robots-Tag`.

**Публикация пересобирает сайт.** Так выбрано осознанно: полная сборка занимает
около 30 секунд, повторная — 7, пик памяти 350 МБ. За эти секунды сайт остаётся
полностью статическим, то есть быстрым, переживающим падение Node и не
требующим базы данных. Динамический блог сэкономил бы эти секунды, но заставил
бы весь сайт зависеть от работающего процесса и потребовал бы переносить
127 статей архива в базу.

Публикация не держит форму открытой: она ставит сборку в очередь и сразу
отвечает, а состояние показывается сверху. Готовая сборка подменяет рабочую
переключением симлинка — одной операцией, так что полусобранного сайта
посетитель не увидит. Сломанная сборка не выкатывается вовсе.

**Записи из админки и архив из git не смешиваются.** Архив 127 статей лежит
в репозитории, всё написанное через админку — в `/srv/pivzavod74/data` на
сервере. Перед сборкой `scripts/prepare-content.mjs` накладывает второе на
первое. Поэтому выкладка новой версии сайта не затирает написанное заказчиком,
а правка архивной статьи не требует коммита. Бэкапить нужно ровно один
каталог — `data`.

### Почему письмо, а не SMTP-сервис рассылок

На VDS доступны обычные TCP-сокеты, поэтому письма уходят напрямую через ящик
заказчика (Яндекс 360, Mail.ru для бизнеса — любой) по SMTP. Внешний сервис
вроде Unisender или Resend не нужен. На Cloudflare Workers, где сайт лежал
раньше, такой возможности нет — там пришлось бы заводить отдельный аккаунт
у почтового провайдера.

Два подводных камня описаны в `deploy/README.md`: нужен **пароль приложения**
(обычный пароль от аккаунта по SMTP не проходит), и у хостера бывает закрыт
исходящий SMTP — открывают по заявке в поддержку.

### Конфиг nginx генерируется

`deploy/nginx/pivzavod74.conf` собирается командой `npm run nginx` из трёх
источников: `public/_redirects`, `public/_headers` и полей `legacyUrl` в
записях блога. Править файл руками бессмысленно — перезапишется.

Что он делает:

- 139 точных редиректов со старых адресов Joomla, из них **127 ведут прямо на
  нужную статью** блога, а не в общий список;
- 18 правил на разделы старого сайта целиком;
- `www` → без `www`, `http` → `https`, причём старый адрес по http уводится
  сразу на конечный, без промежуточного перехода;
- заголовки безопасности, HSTS и кэш: год на хэшированные ассеты, месяц на
  перенесённые фотографии;
- проксирование `/api/` на сервис заявок с ограничением 10 заявок в минуту
  с адреса.

### Что проверено на настоящем nginx

Конфиг не только проходит `nginx -t` — он поднят и проверен запросами:

- статика, 404 на несуществующий адрес, `error_page` на собственную 404-страницу;
- редиректы со старых адресов — и с процентным кодированием (`%D0%A3%D1%87…`),
  и с сырой кириллицей в пути; оба варианта ловит одно правило, потому что
  nginx кладёт в `$uri` уже раскодированный путь;
- `www` → без `www`, `http` → `https`, старый http-адрес одним переходом;
- заголовки и `Cache-Control` по типам файлов;
- форма: заявка проходит и письмо формируется, кривой телефон — 400, honeypot —
  тихий 200, чужой `Origin` — 403, тело больше 16 КБ — 413, GET на `/api/lead` —
  405, превышение частоты — 429;
- при незаполненных настройках почты сервис отвечает 503, а не делает вид,
  что заявка ушла.

Два места, где конфиг не собирался с настройками по умолчанию и это исправлено
в генераторе: кириллические ключи длиннее, чем рассчитывает `map_hash_bucket_size`,
и `http2 on;` не понимает nginx до 1.25 (в Ubuntu 22.04 и 24.04 стоит старее).

## Структура

```
src/
  components/      Сквозные и страничные компоненты
  content/blog/    Записи блога (сюда пишет скрипт миграции)
  data/            Весь копирайт и справочные данные из ТЗ
  layouts/         BaseLayout: head, SEO, Schema.org
  pages/           Маршруты, повторяют карту сайта из раздела 2 ТЗ
  styles/          tokens.css — дизайн-система, global.css — база
server/            app.mjs — точка входа; lead.mjs — заявки письмом
  admin/           админка: вход, записи, загрузка фото, пересборка
deploy/            nginx, systemd, скрипт выкладки
scripts/           migrate-donor.mjs — миграция с донора
                   build-nginx-conf.mjs — сборка конфига nginx
                   prepare-content.mjs — архив + записи из админки
                   admin-password.mjs — хеш пароля для админки
public/            robots.txt, _redirects, _headers, favicon, OG
assets/            Сырые материалы с донора (в git не попадают)
```

Весь текст с сайта вынесен в `src/data/site.ts` и `src/data/content.ts` —
страницы его не хардкодят, правки контента не требуют лезть в разметку.

## Совместимость со старыми адресами

`public/_redirects` переводит разделы Joomla-донора (`/index.php/…`) на новую
структуру 301-редиректами, чтобы ни один старый URL не отдавал 404.
Точечные редиректы отдельных записей блога имеет смысл дописать после
миграции — у каждой записи в фронтматтере сохраняется `legacyUrl`.
