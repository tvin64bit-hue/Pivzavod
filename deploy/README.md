# Установка сайта на сервер FirstVDS

Сайт статический: nginx отдаёт готовые файлы. Динамических частей две, и обе
обслуживает один маленький сервис на Node:

- **форма заявки** — письмо на почту по SMTP;
- **админка на `/admin`** — список новостей, редактор с загрузкой фотографий
  и публикация. Публикация пересобирает сайт заново (около полуминуты) и
  переключает симлинк одной операцией, поэтому полусобранного сайта посетитель
  не увидит.

Базы данных нет: записи лежат обычными markdown-файлами, фотографии — обычными
файлами на диске.

Ниже — установка с нуля. Всё выполняется по SSH под пользователем с sudo.
Дальнейшие выкладки делает `deploy/deploy.sh` одной командой.

## Что понадобится

- VDS с Ubuntu 22.04 или 24.04 (подойдёт минимальный тариф: сайт статический,
  нагрузки почти нет);
- домен `pivzavod74.ru`, у которого A-запись указывает на IP сервера;
- ящик, с которого будут уходить письма (Яндекс 360 для бизнеса — бесплатно
  на своём домене), и **пароль приложения** для него.

## 1. Базовая настройка сервера

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y nginx rsync curl

# Node 20 из репозитория NodeSource — в стандартном Ubuntu версия старее
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs
node -v   # должно быть v20 или новее
```

Файрвол, если включён:

```bash
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
```

## 2. Каталоги

```bash
sudo mkdir -p /srv/pivzavod74/data /var/www/pivzavod74/releases /var/www/certbot
sudo chown -R www-data:www-data /srv/pivzavod74 /var/www/pivzavod74
```

Что где лежит:

| Каталог | Что внутри | В бэкап |
|---|---|---|
| `/srv/pivzavod74` | код сайта, приезжает при выкладке | нет, он в git |
| `/srv/pivzavod74/data` | **новости и фотографии из админки** | **да** |
| `/var/www/pivzavod74/releases` | три последние сборки | нет |
| `/var/www/pivzavod74/current` | симлинк на текущую сборку | нет |

Бэкапить нужно ровно один каталог — `/srv/pivzavod74/data`. Всё остальное
восстанавливается из репозитория и пересборкой.

## 3. Сертификат

Certbot должен получить сертификат до того, как заработает конфиг сайта —
конфиг на него ссылается и без него nginx не стартует.

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot certonly --nginx -d pivzavod74.ru -d www.pivzavod74.ru
```

Продление certbot настраивает сам (таймер `certbot.timer`), проверить:
`systemctl list-timers | grep certbot`.

## 4. Почта для заявок

```bash
sudo cp deploy/pivzavod74.env.example /etc/pivzavod74.env
sudo nano /etc/pivzavod74.env          # впишите MAIL_TO, SMTP_*
sudo chown root:www-data /etc/pivzavod74.env
sudo chmod 640 /etc/pivzavod74.env
```

Два подводных камня:

- **Пароль приложения, а не пароль от аккаунта.** У Яндекса и Mail.ru обычный
  пароль по SMTP не проходит, если включена двухфакторная аутентификация.
  Создаётся в настройках безопасности почтового аккаунта.
- **Исходящий SMTP на VDS часто закрыт.** Хостеры режут порт 25 от спама,
  иногда заодно 465 и 587. Проверьте с сервера:

  ```bash
  curl -v --max-time 5 telnet://smtp.yandex.ru:465
  ```

  Если соединение не устанавливается — напишите в поддержку FirstVDS, что
  нужен исходящий SMTP на 465; открывают по запросу.

## 5. Доступ в админку

```bash
node scripts/admin-password.mjs
```

Скрипт придумает пароль, покажет его один раз и выдаст три строки для
`/etc/pivzavod74.env`: `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH`, `SESSION_SECRET`.
Свой пароль — `node scripts/admin-password.mjs 'мой-пароль'` (не короче
12 символов).

Пароль нигде не хранится: в файл идёт только хеш, обратно его не восстановить.
Забыли — сгенерируйте заново и перезапустите сервис.

## 6. Сервис

```bash
sudo cp deploy/pivzavod74.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now pivzavod74
systemctl status pivzavod74 --no-pager
curl -s http://127.0.0.1:8787/api/health    # {"ok":true,"mail":true}
```

`"mail":false` означает, что переменные почты в `/etc/pivzavod74.env`
заполнены не полностью — сайт и админка работают, но заявки сервис будет
отклонять, а форма честно покажет ошибку и предложит позвонить.

Логи: `journalctl -u pivzavod74 -f`.

## 7. Первая выкладка

С рабочей машины, из корня проекта:

```bash
SSH_TARGET=root@адрес-сервера ./deploy/deploy.sh
```

Скрипт зальёт исходники и конфиг nginx, поставит зависимости, перезапустит
сервис и попросит его собрать сайт.

Сборка идёт **на сервере**, а не на рабочей машине, и это принципиально:
записи, созданные заказчиком через админку, живут в `/srv/pivzavod74/data`.
Собрать сайт у себя и залить готовый `dist` значило бы выкатить его без них.

## 8. Проверка

```bash
curl -I https://pivzavod74.ru/                       # 200
curl -I https://www.pivzavod74.ru/                   # 301 на без-www
curl -I http://pivzavod74.ru/index.php/2.html        # 301 на /o-kompanii
curl -I https://pivzavod74.ru/net-takoy-stranicy     # 404
```

И два сквозных прохода:

- отправьте заявку через форму на сайте и убедитесь, что письмо пришло.
  Если не пришло, смотрите `journalctl -u pivzavod74 -n 50` — там причина
  отказа SMTP;
- зайдите на `https://pivzavod74.ru/admin`, создайте черновую новость,
  загрузите фотографию, опубликуйте. Через полминуты она должна открыться
  по своему адресу. Потом удалите её — список должен вернуться к прежнему.

## Как это работает изнутри

**Публикация — это пересборка.** Сайт статический, поэтому «опубликовать»
значит собрать заново: примерно 30 секунд на холодную и около 7 на повторную.
Форма не ждёт: она ставит сборку в очередь и сразу отвечает, а админка
показывает состояние сверху. Если во время сборки опубликовать ещё раз,
следующая запустится после текущей — ровно один раз, сколько бы правок
ни накопилось.

**Готовый результат подменяет рабочий переключением симлинка.** Сборка идёт
в `releases/<метка времени>`, и только когда она успешно закончилась,
`current` начинает указывать на неё. Сломанная сборка не выкатывается: сайт
остаётся прежним, а в админке появляется сообщение об ошибке.

**Записи из админки и архив из git не смешиваются.** `scripts/prepare-content.mjs`
собирает каталог `.content/blog` из двух источников: 127 статей архива из
репозитория и всё, что заказчик написал через админку, из `data/posts`.
Одноимённые файлы админки перекрывают архивные, слаги из `data/deleted.json`
отбрасываются. Поэтому правка архивной статьи не требует коммита, а выкладка
новой версии сайта не затирает написанное заказчиком.

Удалить архивную статью насовсем нельзя — она вернётся при следующей
выкладке, — поэтому «удалить» заносит её слаг в `deleted.json`. Своя запись
удаляется вместе с файлом.

**Фотографии не попадают в сборку.** Они лежат в `data/uploads/ГГГГ/ММ/`
и раздаются nginx напрямую по адресу `/uploads/…`. Если бы они лежали внутри
`dist`, каждая публикация их бы теряла. При загрузке снимок разворачивается
по EXIF и ужимается до 1600 пикселей по ширине: с телефона приходит 4000
пикселей и 5 МБ, и страница новости весила бы как весь остальной сайт.

## Про конфиг nginx

`deploy/nginx/pivzavod74.conf` **генерируется**, править его руками
бессмысленно — перезапишется. Источники правил:

- `public/_redirects` — адреса старого сайта на Joomla;
- `public/_headers` — заголовки и кэш;
- поле `legacyUrl` в записях блога — точечные редиректы на 127 статей.

Пересобрать: `node scripts/build-nginx-conf.mjs`.

Две особенности, на которые стоит обратить внимание при правках:

- **Кириллица пишется буквами, а не процентными кодами.** nginx кладёт в `$uri`
  уже раскодированный путь, поэтому одно правило ловит и `%D0%9D…`, и сырой
  UTF-8. На Cloudflare было наоборот, и файл `_redirects` до сих пор хранит
  коды — генератор раскодирует их сам.
- **`map_hash_bucket_size 256`** обязателен: русские ключи вдвое длиннее
  латинских, и с настройками по умолчанию nginx отказывается собирать карту.

## Если IPv6 включён

Конфиг слушает только IPv4 — так он стартует на любом сервере. Если у VDS есть
IPv6, добавьте рядом с `listen 443 ssl http2;` строку
`listen [::]:443 ssl http2;` (и `listen [::]:80;` в первом блоке) — но не в
сгенерированном файле, а в `scripts/build-nginx-conf.mjs`, иначе потеряется
при следующей сборке.
